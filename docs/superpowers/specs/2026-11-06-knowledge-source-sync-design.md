# Continuously synced knowledge sources — Google Drive

**Status:** Proposed design; no application behavior described below is shipped unless explicitly listed in §2.  
**Date:** 2026-11-06
**Companion designs:** [Quality-gated publishing](2026-11-06-quality-gated-publishing-design.md) and [Eval-backed run repair](2026-11-06-eval-backed-run-repair-design.md).

## 1. Product decision and scope

Build **Google Drive as the first fully supported, read-only source connector** for existing user-owned Knowledge libraries. A user connects a Google account, selects individual files or recursive folders, reviews the import boundaries, starts an initial sync, and then receives automatic incremental updates with explicit freshness and failure states. Google Drive is the decision, not an unresolved Drive-versus-Notion alternative.

The unit consumed by retrieval is an **immutable KnowledgeRevision**. To prevent release regressions across both RAG consumption surfaces without inventing a second snapshot format, KnowledgeRevision uses a shared schema with strict XOR scope: either a shared user library (`knowledge_base_id`) or workflow-local knowledge (`workflow_id`). Google Drive connectors remain library-scoped only (`knowledge_sources.knowledge_base_id` is required), while manual paste/file/URL/bulk ingestion and deletions on both libraries and workflows build sealed revisions through the identical sealing and refcount machinery. Synchronization advances the library's active revision for preview/live consumers. Newly quality-gated releases pin a revision and never silently consume the next sync or local edit. Permission loss, source deletion, exclusion, or disconnect can deny historical content regardless of that pin. Reproducibility is subordinate to authorization.

### Goals

- Useful unattended ingestion for a selected Drive corpus, including supported shared-drive folders, not a one-time OAuth/file-picker demonstration.
- Correct recursive membership, changes, removals, duplicate handling, retry/recovery, and atomic visibility.
- Clear answers to “what is searchable?”, “how fresh is it?”, “why did it stop?”, and “what happens to my published workflows if I disconnect?”.
- Preserve owner isolation, existing paste/file/public-URL/bulk ingestion across both library and workflow-local knowledge, source citations, retrieval settings, and Google/lexical retrieval capabilities.
- Provide the unified revision/read contract required by both companion specs for both library and workflow-local knowledge nodes, without duplicating their manifest, evaluation-snapshot, or release-check schemas.

### Non-goals

Notion, S3, other connectors, write-back to Drive, creating/editing Drive files, service accounts/domain-wide delegation, organization/RBAC expansion, per-document end-user ACL mirroring, OCR, image/audio/video retrieval, Sheets/Slides extraction, comments/suggestions/revision-history ingestion, following shortcuts, Google push notification channels, and deterministic LLM output. Polling is the complete first delivery mechanism, not a temporary webhook scaffold. The selected owner's Drive permissions are the boundary; library publication may expose retrieved knowledge to that workflow's existing consumers and must say so before connection.

## 3. Provider facts and explicit connector policy

Primary references were read on 2026-11-06. Google documentation establishes provider behavior; numeric Aegis limits below are product choices, not claims about Google's limits.

### 3.1 Authorization scope and operational eligibility

Request exactly `openid email https://www.googleapis.com/auth/drive.readonly`, offline authorization. `openid/email` identify the connected Google account; they do **not** log the user into Aegis or change its owner. Drive's scope [views/downloads all accessible Drive files and is restricted](https://developers.google.com/workspace/drive/api/guides/api-specific-auth). The narrower `drive.file` permission is per-file, not a promise that selecting a folder grants every existing/future descendant. We choose broad **read-only** authorization because unattended recursive membership discovery is essential, while Aegis imports only explicit selections. The UI must disclose both boundaries accurately.

Public distribution requires restricted-scope verification and, because Aegis stores/transmits this data server-side, the applicable security assessment and Google User Data Policy compliance. A deployment must configure a dedicated Web application OAuth client and approved exact callback URI. A Workspace administrator can block the grant. External OAuth projects in Testing issue seven-day refresh tokens for this scope; Google also documents a 100-refresh-token-per-account/client limit, six-month inactivity expiration, revocation, and time-based access expiration ([token lifecycle](https://developers.google.com/identity/protocols/oauth2#expiration)). Do not work around administrator restrictions, repeatedly mint grants, or describe testing credentials as unattended production-ready.

Shipping prerequisites are explicit: approved/eligible OAuth client for the target distribution, privacy/data-deletion disclosure, allowed model-processing disclosures, authenticated owner mapping, a working encryption key, and a running durable worker. Missing prerequisites produce `connector_unavailable` with administrator setup guidance; the existing manual Knowledge features remain available.

### 3.2 Selection and hierarchy

A Drive connection belongs to one Aegis owner and a validated Google `sub`. A library may have one Drive source per connection; that source contains up to **20 explicit roots**. Each root is either one file or a folder with `recursive=true` (the only supported folder mode). The picker is Aegis's server-backed browser, not a browser-side Google token integration. Tabs: My Drive, Shared with me, Shared drives. Also accept a Drive file/folder ID or a recognized Google Drive/Docs URL, parse only its identifier, and resolve it with the fixed Drive API; never fetch arbitrary supplied URLs.

- Root selection is ID-based. Renames do not create new sources. A selected folder moved within its same corpus remains the selected folder; files moved out of all selected folders stop belonging unless explicitly selected elsewhere in this source.
- Overlapping roots are a union. A child reached through three selected roots is one imported document, with three membership paths recorded.
- Recursive enumeration uses `files.list(q="'<folder_id>' in parents and trashed = false")` and a persisted breadth-first folder frontier. `parents` is **direct membership**, not recursive ([search semantics](https://developers.google.com/workspace/drive/api/guides/search-files)). Include folders in enumeration even if their own MIME is not ingestible. Track visited IDs; cap depth at 30, total discovered files/folders at 10,000 and supported included files at 2,000 per source. Crossing any cap fails the scan visibly; it does not silently truncate membership.
- The numeric discovery/file caps are hard ceilings, not a promise that default quotas can keep that corpus authorized. Selection/activation also passes the access-validation capacity admission rule in §8; an oversized folder requires narrower selection or an operator-approved quota increase, never silently expiring most of its receipts after a successful import.
- Shortcuts (`application/vnd.google-apps.shortcut`) are listed as excluded with reason `shortcut_not_followed`; they never expand the selection, cross a permission boundary, or produce cycles. Select the actual target explicitly to import it. Resource-key-only link shares that cannot be resolved through the account without a resource key are unsupported, with `direct_account_access_required`; do not persist URL resource keys.
- Shared drives are supported only when the connected account is a **member** of the drive and the drive is returned by the paginated `drives.list`. Individual items shared to a non-member from a shared drive are visibly unsupported for this release. This restriction gives each selected shared corpus a usable drive change log rather than relying on incomplete user-log coverage.
- For shared-drive enumeration use `corpora=drive,driveId=<id>,includeItemsFromAllDrives=true,supportsAllDrives=true`; user corpus uses `corpora=user`, `spaces=drive`, appropriate parent filter, and `supportsAllDrives=true`. Never use `allDrives` to infer completeness. Shared-drive root means its drive root folder ID. A root that changes corpora enters `selection_changed` and requires explicit reselection/full reconciliation before importing from the new corpus; it is not followed silently.
- Detect `capabilities.canDownload=false`, trash, access loss, and unavailable roots; no abuse override or protected-content bypass. Parent capability changes require descendant revalidation: the provider does not emit one change per inheriting child ([change semantics](https://developers.google.com/workspace/drive/api/guides/about-changes), [shared-drive parameters](https://developers.google.com/workspace/drive/api/guides/enable-shareddrives)).

### 3.3 Exact content support

| Drive MIME | Download/export operation | Aegis representation |
| --- | --- | --- |
| `application/vnd.google-apps.document` | `files.export(fileId,mimeType="text/plain")` | UTF-8 plain text; title and original Drive URL stored separately. Only exported text, not comments, suggestions, images or layout. |
| `application/pdf` | `files.get(fileId,alt=media,supportsAllDrives=true)` | Existing PDF text extractor, at most 200 pages; no OCR. |
| `application/vnd.openxmlformats-officedocument.wordprocessingml.document` | Same blob download | Existing DOCX paragraph extraction; tables, images and layout are not promised. |
| `text/plain` | Same blob download | UTF-8 text. |
| `text/markdown`, `text/x-markdown` | Same blob download | Markdown text, no embedded asset fetching. |
| `application/octet-stream` **only with** `.txt`, `.md`, or `.markdown` name | Same blob download | Text decoder; reject binary/NUL-bearing data. No extension override for PDF/DOCX masquerading as another MIME. |

Folders are traversal metadata, never documents. All other MIME types, including Google Sheets, Slides, Drawings, Forms, legacy Office, HTML, archives, images, audio and video, are `unsupported_type` and excluded before download. This explicitly avoids importing only the first sheet of a spreadsheet: Google [CSV/TSV exports are first-sheet-only](https://developers.google.com/workspace/drive/api/guides/ref-export-formats). Google Docs plain-text export is supported by that same table. No alternate export fallback changes the content representation.

Check `canDownload` before transfer. Google [limits `files.export` to 10 MB](https://developers.google.com/workspace/drive/api/guides/manage-downloads#export-content); Aegis imposes its stricter **8 MiB** streamed-byte cap on exports and blobs. MIME canonicalization supplies the parser's trusted synthetic extension rather than trusting a misleading remote filename. Decode UTF-8 with replacement as the existing parser does and report replacement count; reject binary content. Enforce 2,097,152 extracted characters on every type and the existing decompression ratio guard; connector imports with `truncated=true`, unreadable/encrypted PDF, no extracted text, or parse failure are errors, not healthy partial documents. Return a concrete reason and offer exclude/retry. Existing manually imported truncated documents retain their current semantics but carry migration provenance.

## 4. User journey and UI contract

The Knowledge page retains Libraries, Add documents, and Try a query. Add a **Sources** section above Documents and a **Sync activity** drawer. Use existing warm near-black/bone surfaces, compact tables, semantic status colors only, Radix dialogs, keyboard focus management, and sonner for short action feedback. Status and error information must remain in the page, not only in disappearing toasts.

1. **Connect.** “Connect Google Drive” explains read-only broad authorization, selected-only ingestion, text limitations, background polling, model-processing consequences, and that workflow consumers can receive selected knowledge. It opens the OAuth flow in the current tab. Missing setup has an actionable disabled state. Viewer keys see metadata/status but no connection/source controls and cannot browse the wider Drive account through the API.
2. **Select.** Return to the same library with a connected-account label. Browse/search paginated server results, select files/recursive folders, see shared-drive identity, exclusions and configured limits. No import starts on OAuth success alone. Root names/counts are estimates until enumeration finishes; never display a false exact total. A single “Start sync” POST saves selections and enqueues atomically.
3. **Initial sync.** A source row shows `Queued → Discovering → Downloading/Indexing → Activating → Up to date`, discovered/included/downloaded/indexed counts, skipped-type count, errors, start time, and cancel. Indeterminate progress during discovery becomes processed/known counts once discovery ends. The prior active library remains searchable; a new empty library shows “No synced revision yet.” No staging chunk appears in query results.
4. **Incremental operation.** Show last successful content check, last content change/activation, next scheduled check, active revision sequence, and access-valid-until separately. “Up to date” means checked at that time, not real-time. Sync now is idempotently coalesced with existing work. A no-change run updates freshness without creating an identical revision.
5. **Failure.** Quota/network errors show retry time and last-good revision. Authentication errors show “Reconnect account”; missing roots/download restrictions show “Access lost”; parser/cap errors show affected documents with Retry or Exclude. Unsupported types are a counted neutral exclusion, not an error. Never call a source healthy while a supported accepted file failed. Old content may remain usable only while its authorization receipts are valid.
6. **Retry/cancel/pause.** Retry starts from committed checkpoints or full reconciliation when required. Cancel stops this job, not the source schedule; UI also offers “Pause automatic updates.” Pause suppresses content refresh but **not** permission checks. “Resume updates” schedules immediate reconciliation. Cancel cannot undo an already-committed activation and cannot roll back a safety tombstone; report which occurred.
7. **Document detail.** Show account/source, root membership, Drive filename/link, MIME/export type, provider modified time/version, imported time, local content hash, active document-version ID, status/reason, and chunk count. Source-owned documents cannot be edited as pasted text. Exclude is explicit and persists by remote file ID; reinclude creates a new authorized version rather than reviving a denied historical version.
8. **Disconnect/delete.** Source removal explains affected library revisions and published workflows using their manifests. Connection disconnect lists all attached sources. Confirm “Stop access and remove synced knowledge”; no keep-searchable-copy option. Local denial is synchronous even if remote token revocation/physical purge is pending. A metadata-only “Disconnected; deletion pending” row remains for the stated retention window.
9. **Query/release integration.** The query panel defaults to the active revision and shows `Revision 12 · checked 3m ago`. It can select an allowed retained revision, with “historical” label; unsaved settings are a labeled preview override. Published workflow UI shows `Pinned revision 11; active 12` and links to [a new quality check](2026-11-06-quality-gated-publishing-design.md). Clicking this never auto-publishes. [Run repair](2026-11-06-eval-backed-run-repair-design.md) shows the knowledge revisions actually used and cannot turn revoked content into fixtures.

### State presentation

Connection state is `connected | reauth_required | disconnecting | disconnected`. Source state is `pending | syncing | ready | blocked | paused | disconnected`; orthogonal fields are `last_error_code`, `freshness_status=fresh|stale|unknown`, and `access_status=allowed|expired|denied`. Job state follows §8. A ready source is fresh when the last successful content check is at most 10 minutes old; older checks are stale. Paused sources show paused plus content age, never fresh by implication. Access status overrides optimistic UI: expired/denied content is not searchable even if a successful content sync exists.

## 5. OAuth and encrypted token lifecycle

Use `google-auth-oauthlib.flow.Flow` with a **Web** client, server-side code exchange, and explicit PKCE S256. The library supports a verifier and both web/installed client types ([library reference](https://google-auth-oauthlib.readthedocs.io/en/latest/reference/google_auth_oauthlib.flow.html)); Google's [PKCE description](https://developers.google.com/identity/protocols/oauth2/native-app#step-1:-generate-a-code-verifier-and-challenge) defines the 43–128 character verifier/S256 transformation. This design adds PKCE to the confidential-client flow; it does not switch to a desktop client or rely on PKCE alone as CSRF protection.

### Start, callback, and completion

- Authenticated editor POST creates an OAuth attempt bound to `user_id`, intended library, optional reconnect connection ID, a hash of the initiating API-key identity, a 256-bit random state, independent OIDC nonce, 64-character random verifier, and a ten-minute expiry. Persist state/browser-secret/nonce hashes; verifier and temporary token payload are encrypted. No raw API key is stored.
- Because Aegis currently uses header API keys rather than a universal browser login cookie, introduce a short-lived **flow-only** HttpOnly, Secure, SameSite=Lax browser-binding cookie through a same-origin Next proxy. It is not Aegis API authentication and never authorizes other routes. Start uses normal auth headers and verifies Origin; callback checks cookie plus state. Local HTTP development is allowed only for explicitly configured loopback origins, not arbitrary hosts.
- Redirect to `https://accounts.google.com/o/oauth2/v2/auth` with configured client ID/exact redirect URI, `response_type=code`, exact scopes, `access_type=offline`, `state`, `nonce`, `code_challenge_method=S256`, and challenge. Use `prompt=consent` for first connection or reconnect requiring a new refresh token, not on routine sync. Do not enable `include_granted_scopes`; the connector client is dedicated to this feature.
- Callback is the single explicitly unauthenticated callback route, with strict state+browser binding validation. CAS attempt `pending → exchanging` before code exchange; reject expired, mismatched, consumed, duplicate and error callbacks without storing a grant. Callback exchanges code with client secret and verifier using bounded HTTP timeouts. On ambiguous exchange failure expire the attempt and restart OAuth; never replay a consumed authorization code indefinitely.
- Validate ID-token signature against Google's rotating keys, issuer, audience/client ID, expiry and nonce; require stable `sub`, store verified email only for display ([OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)). Confirm required granted scopes from token response; partial consent is not a connected source. Reconnect must yield the same `sub`; switching Google accounts requires a new connection. An existing same-owner/same-client/same-sub connection is reused rather than multiplying refresh tokens.
- Store encrypted token material on the attempt as `awaiting_completion`, then 303 redirect to a fixed same-origin `/knowledge?library=<uuid>&connect_attempt=<uuid>`. Never put tokens, API keys, codes, or provider errors in that redirect. Redact callback query strings from access logs, return `Cache-Control: no-store`/`Referrer-Policy: no-referrer`, and render no third-party scripts on callback pages.
- The returned page calls authenticated editor POST completion. Recheck current owner/key authorization, flow binding, expected account, expiry and connection uniqueness, then atomically install the grant and consume/delete attempt secrets. This second step prevents a revoked/reassigned initiating key from creating a live grant via a headerless callback. Lost callback/browser completion requires restart after expiry; attempt material is purged within one hour, and abandoned grant tokens get a bounded revocation attempt before deletion.

### Token handling

Create a dedicated `knowledge_connections` record, not a general `Credential` selectable by an agent node. Reuse the Fernet primitive only after `encryption_enabled()` succeeds; require authenticated deployment (`auth_enabled=true`) and a valid key for start, callback, refresh and token writes. No plaintext fallback. Client secret lives in Settings/configured secret storage, never rows, frontend config or manifests. Tokens are encrypted with the existing key namespace, decrypted only inside the connector/token-refresh service, and never returned by list/detail APIs.

Access tokens expire from provider `expires_in`; refresh at least 60 seconds before expiry. Serialize refresh per connection using a separate 60-second refresh lease and fencing token; concurrent workers await/re-read the installed token rather than issue competing refreshes. Preserve the existing refresh token when Google omits a replacement; install rotated refresh/access tokens atomically with token version CAS. Honor `refresh_token_expires_in` when supplied. A transient token endpoint failure is retryable; `invalid_grant`, missing required scope, account mismatch or admin block moves to `reauth_required` and denies all linked source content immediately when observed. `401` from Drive permits one refresh and replay; a second `401` is reauth, not an endless loop.

`token_version` changes on ordinary token replacement; **semantic `credential_generation` changes only on identity/scope/authorization changes or disconnect**. Ordinary refresh does not invalidate every release check. Restore after reauth requires full permission/content reconciliation and new source access epochs; previously denied revisions remain denied. Encryption-key rotation is an operator maintenance operation: pause connector execution, re-encrypt all grant/attempt/revocation-outbox material under the replacement key in a controlled transaction/batches with a retained old-key reader, then switch writers/remove the old key after verification. A decrypt failure is `encryption_unavailable`, fails closed and never sends ciphertext to Google.

Disconnect first increments semantic generation, denies attached sources, cancels jobs and removes token material from normal execution access. Put only the encrypted revocation token into a restricted revocation-outbox row for up to 24 hours; POST it in the body to Google's [revoke endpoint](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke). Retry transient failures, then erase material regardless and instruct the owner to remove access in Google Account permissions if remote revocation was not confirmed. Revocation can affect a combined Google grant; use a dedicated client and disclose that disconnect affects all this owner's linked sources for the account. Removing one source does not revoke a connection still used elsewhere.

## 6. Durable storage and immutable revision contract

All new IDs/FKs are SQLAlchemy `Uuid`/Alembic `sa.Uuid`, timestamps UTC, JSON uses the repository dialect abstraction. All user-owned rows carry `user_id` and enforce same-owner parent references with composite unique/FK constraints where relationally possible, plus service checks. Nullable workflow-scoped legacy chunk fields remain untouched by library cutover. No OAuth material is placed in job payloads, reports, manifests, hashes, or audit JSON.

### 6.2 Sealing and activation

Build a candidate whole-library or whole-workflow membership by replacing affected members in the current active revision, preserving untouched manual or other-source members. For workflow-local knowledge, manual paste/upload/bulk/delete actions construct and activate workflow revisions using this exact sealing process without connector overhead. New chunks/versions remain unreachable staging data. Finalization validates complete discovery/ingest, processed accepted files, explicit exclusions, limits, profile consistency, ownership and live authorization. Unsupported-type omissions are intentional; supported-file parse/download/index errors block activation until fixed or explicitly excluded. No “successful partial sync” quietly omits an accepted document. Empty selections/all unsupported files can activate a valid empty source contribution, with a visible zero-import warning.

In **one database transaction**:

1. Re-read source config/credential generations, source epochs, cancellation flag, unexpired worker lease/fence, and current library activation/access generations.
2. Rebase the source replacement on the latest active revision if another source/manual ingest won. Do not redo downloads unnecessarily. Revalidate source membership, current exclusions and limits after rebasing.
3. Insert the sealed revision and ordered member rows; calculate canonical SHA-256 over sorted stable membership IDs/version hashes, citation metadata, processing profile and saved retrieval settings. Exclude timestamps, cursor/token values and mutable access generations from the content hash. If canonical content equals the active revision, reuse its ID instead.
4. CAS `active_revision_id`/`activation_generation` on `knowledge_bases` (or `active_knowledge_revision_id`/`knowledge_activation_generation` on `workflows`); commit source observation state and all source corpus cursors together with terminal successful job state/freshness. Losing the CAS rolls back this candidate and retries finalization against the new active revision, not a new external import.

Activation never depends on best-effort vector mirrors. Stored JSON vectors and revision-constrained lexical/vector candidates are authoritative; initial delivery uses exact scoring over the bounded selected revision, reusing existing library retrieval. Accelerated vector paths may only run when they accept revision membership as a prefilter, not global top-K followed by filtering. Orphan mirrors cannot return text without an authorized member join. Chunk/vector purge can be asynchronous because reads enforce membership/denials first.

Security denial commits are intentionally independent of this activation transaction: a removal discovered in an otherwise failed/cancelled sync must still make old content unavailable. Subsequent reconciliation can activate a clean revision containing the remaining allowed documents. Do not wait for embedding success to hide revoked content.

### 6.3 Immutable read seam shared with publishing and repair

Proposed service signatures (not current symbols):

```text
resolve_active_revision(db, user_id, *, knowledge_base_id=None, workflow_id=None)
  -> {revision_id, content_hash, settings_hash, access_generation, scope_kind, scope_id}

assert_revision_allowed(db, user_id, revision_id)
  -> AccessStamp {scope_kind, scope_id, revision_id, access_generation, valid_until}

query_revision(db, user_id, revision_id, *, query,
               settings_override=None, tags=None, top_k=None, method=None)
  -> {revision_id, content_hash, access_generation, scope_kind, scope_id, query, method, settings,
      rewrite, rerank, results, citations}
```

`assert_revision_allowed` verifies owner and matching scope (`knowledge_base_id` or `workflow_id`), sealed content availability, every member's source/document epoch against live denial overlays, connection availability (for Drive sources), and Drive member access receipts. Any denied member rejects the **whole revision**, including a query whose tags would not have selected that member. For provider-synced content (Google Drive), expired receipts return `knowledge_access_unverified` and request immediate access validation; callers cannot opt into stale authorization. For purely manual content (both in libraries and workflow-local knowledge), `valid_until` is `None` (unaffected by external receipt deadlines) and validity depends solely on un-denied member status. A missing/purged revision returns `knowledge_revision_unavailable`, never active fallback. Validation/reads at execution start, each retrieval, before external model/tool dispatch using that content, and response/evaluation completion compare `access_generation`; a change forces a fresh check and suppresses newly produced output if denied. A transaction serializes publish's access-generation check with tombstone commits.

Authoritative permission dependency for manifests, evaluation snapshots and repair is `{revision_id, content_hash, scope_kind, scope_id, access_generation}`. Downstream diagnosis and repair bundles carry this exact dependency; any access generation mismatch or tombstone invalidates even cached or copied fixture text.

All `kb_retrieve` nodes resolve through this seam, dispatching to `knowledge_base_id` or `workflow_id` according to the node's configured target. An ordinary preview without a manifest resolves active once at run admission and pins for that run, preventing mid-run source drift. Quality-gated `ExecutionManifest` binds revision ID/hash and effective retrieval config/profile; it must not use mutable library or workflow defaults. Existing published deployments may remain explicitly **legacy live/unattested** until migrated under [quality-gated publishing](2026-11-06-quality-gated-publishing-design.md); that is not an exception for any newly gated publication.

Retrieval cache keys include owner, revision, effective settings, query and access generation. Authorization is rechecked even on a cache hit. Citations include `knowledge_base_id,revision_id,source_id,source_document_id,document_version_id,chunk_id,provider_file_id,source_name,source_url,provider_modified_at,imported_at,char_start,char_end,rank,score`; source URL is a canonical Google UI link without authorization parameters. Provenance follows outputs into run results, checkpoints, session context, recorded fixtures and repair/evaluation inputs. Those readers must validate dependency revisions before reuse; copied retrieval text does not become a permission bypass.

Existing embedding/rewrite behavior is not sufficient for immutable execution. Revision builds choose and persist either `local_hashing_v1` (768 dimensions; explicitly labeled, no remote embedding calls) or the configured Google embedding model+dimension+credential semantic generation, then use that same profile for query embeddings. Default new connected libraries to `local_hashing_v1` with BM25/hybrid retrieval unless the owner explicitly enables disclosed Google embedding processing. A remote embedding failure blocks build/query instead of silently falling back. A configured LLM rewrite/rerank failure is explicit unavailable/incomplete execution in a pinned manifest, not a claimed successful stage. Normal preview may offer an explicit user-chosen local-only query, visibly marked as a different settings override. Changing profile/chunk settings requires rebuilding the complete library into a new revision. Saved retrieval-only settings create a metadata/settings revision; library name/description changes do not change executable content.

## 7. Sync algorithm, removals and freshness

### 7.1 Initial/full reconciliation

1. Claim source work with source config/credential generations and a library baseline. Validate all roots and selected shared-drive memberships. Acquire a **start page token before enumeration** for the user log and every selected shared-drive log (`changes.getStartPageToken`, `supportsAllDrives=true`, drive ID for drive logs).
2. Persist the initial token set and folder frontier. Enumerate every page of every root using a narrow field mask: `id,name,mimeType,parents,driveId,version,modifiedTime,size,md5Checksum,trashed,capabilities(canDownload),webViewLink`; `nextPageToken,incompleteSearch` on list envelopes. Metadata for unrelated change-log entries is discarded after membership classification; do not build an owner-wide content catalogue.
3. Continue until `nextPageToken` is absent, even after empty/short pages. `incompleteSearch=true` is an incomplete scan, never an empty source. If a `files.list` token is rejected, restart that folder's page enumeration and dedupe by ID; the provider [documents that list tokens may be rejected and typically last hours](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list). Do not mark missing files removed from an incomplete scan.
4. Determine union membership and accepted MIME types. Fetch metadata before transfer and again after transfer; require the same provider `version` and readable membership/capabilities. If changed, discard staged content and retry that file up to three times; continuously changing files block this sync with `file_changed_during_download`, not fabricated point-in-time content. Hash the actual downloaded/exported bytes and normalized parsed text. Provider version is an opaque remote change marker, **not** a downloadable Google revision ID and not the local KnowledgeRevision.
5. Parse, chunk, and embed/version only changed content/profile; reuse allowed identical versions. Stream cap enforcement and time limits apply regardless of metadata size claims. Stage every accepted file or an explicit error.
6. Replay changes from the saved pre-scan tokens through each terminal `newStartPageToken`, applying affected file/folder membership and re-fetching changed descendants. This closes the initial enumeration race. Drain terminal pages for each corpus; if changes invalidate already-staged versions, rebuild affected files. Google is not providing a cross-file atomic snapshot: the local revision is an internally consistent set of observed stable file versions, with sync start/end times, not a claim that all Drive files were frozen at one instant.
7. Revalidate access/membership for all included files and roots at finalization, then activate atomically under §6.2. Full-reconciliation absence can remove a known member only after the relevant traversal completed successfully and a direct metadata/membership check confirms removal, trash, exclusion, loss of capability/access, or departure from all roots. Confirmed security denial is immediate even if another file blocks activation.

### 7.2 Incremental polling

Schedule content polling every **5 minutes** with per-source jitter of up to 30 seconds; no overlap per source. On no-change cycles, update content-check time and cursor without creating a revision. Full recursive reconciliation runs every **24 hours**, after selection/reconnect changes, and after a lost/corrupt cursor. Worker restarts resume a staged checkpoint; downtime coalesces to one due job, not a burst of every missed interval.

Replay the **user log and each selected member shared-drive log**: [user logs alone are insufficient for shared-drive members](https://developers.google.com/workspace/drive/api/guides/about-changes). Use `pageSize=1000,includeRemoved=true,includeCorpusRemovals=true,supportsAllDrives=true,includeItemsFromAllDrives=true,spaces=drive`; `driveId` only for drive log. Persist intermediate next-page tokens in job work, never over the committed source cursor until all required changes/activation commit. [Change tokens do not expire](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes/list); do not invent a periodic expiration/renewal rule. If Google rejects one or local token state is lost, conservatively full-reconcile instead of skipping to “now.” Page replays are idempotent by remote ID/version and staged work PK; process current state, not an assumed append-only delta sequence.

For a changed file, fetch current metadata and resolve its parent chain against selected roots with a visited set/depth cap. This admits files moved into a folder and excludes files moved out. For folder moves/capability changes, recompute its entire known descendant subtree and enumerate newly admitted descendants even if those descendants did not emit changes. For a shared-drive membership removal, deny the entire relevant source contribution immediately and require reconnect/reselection; do not merely drop its cursor. Duplicate appearances in user and drive logs converge on the same remote file identity.

The v3 change resource uses **`removed`**, not the overview's generic “deleted” wording ([REST schema](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes)). `removed=true` may mean deletion, loss of access or a corpus move. If `includeCorpusRemovals` supplies a still-accessible file, validate current membership; otherwise direct-get the known file. Confirmed 404, permission-denied reason, trash, no-download capability or out-of-scope membership creates a denial; a retryable 429/5xx is not evidence of deletion. If disambiguation is unavailable, immediately quarantine that file/revision as access-unverified while retrying; never keep serving a potentially removed file by treating it as an ordinary stale content update.

### 7.3 Access receipts and offline behavior

Content freshness and authorization freshness are distinct. Every source has a permission-validation pass at least every **5 minutes**, including when automatic content refresh is paused. It probes current roots, shared-drive membership, and metadata/download capability/membership for the union of remote files retained in **any referenced or retained revision**, not just today's active members. Successful per-file receipt lifetime is **15 minutes from that file's check**, bound to connection semantic generation and source/document epochs. Ancestor/membership observations have the same maximum lifetime. This pass does not download unchanged content or create revisions.

A provider permission loss can occur after a successful check. Aegis cannot know it instantaneously: the maximum stale authorization window is 15 minutes under these receipt rules, often detected by the next five-minute poll, subject to Google revealing the change. At receipt expiry retrieval fails closed even if Google/worker is unavailable. UI reports this exact tradeoff; it must not promise instant remote revocation detection. Local disconnect/exclude/delete and observed revocations deny access in their committing transaction. Reading a pinned revision never extends a receipt. A protected publish requires current valid receipts plus the generation CAS; newly queued validation work is not a pass.

### 7.4 Denial versus deletion versus restoration

- **File deletion, trash, access/download restriction, or removal from all selected roots:** append a document denial through its current epoch, increment library access generation, invalidate affected revision caches/checks, and omit from the next active revision. `404` cannot distinguish deleted from forbidden, so display “Removed or no longer accessible,” not a fabricated precise cause.
- **Source exclusion/root removal/local source delete:** the same denial is immediate. Configuration edits are additive-safe but removals must deny any members no longer permitted, before background rebuild. If overlap still permits a member, retain it; do not deny merely because one path disappeared.
- **Connection revoke/disconnect:** source-level denial through current source epoch for all linked sources/libraries, job cancellation, token lifecycle per §5. A library delete denies all revisions before physical deletion; manifests remain metadata references explaining why invocation is blocked.
- **Return/reconnect/untrash/reinclude:** revalidate roots/account, increment the appropriate epoch and build a **new** version/revision. Tombstones are permanent for old epochs. Old pinned releases do not revive automatically; they require a new candidate/check/publication.
- **Ordinary content edit or parse/index/network failure:** no security denial solely because bytes changed or an import failed. Last-good pinned content may remain readable while access receipts remain valid, with current sync error/freshness clearly shown. Failed initial imports never become searchable.

## 8. Worker ownership, leases, cancellation and budgets

The publishing spec owns the shared durable job machinery. This feature registers `knowledge_source_sync`, `knowledge_source_access_check`, `knowledge_revision_rebuild`, `knowledge_source_purge`, and `knowledge_oauth_revoke` handlers, using its exact generic columns in §6.1. Domain-specific phases/cursors/generations live in knowledge rows, not additional generic job status columns.

- Shared job states retain the existing `queued → running → completed` vocabulary, adding `cancelled` alongside `failed`; retryable work returns to `queued` with `next_attempt_at`. Knowledge UI may display “retrying” from that timestamp/attempt state. Do not introduce a second `succeeded` terminal value or rename unrelated historical jobs.
- Database CAS claims due queued work with a fresh `lease_token`, **60-second lease**, **15-second heartbeat**, and incremented `attempt_count`. Every progress/domain write, cursor advance, activation and terminal transition is fenced by that token plus unexpired lease. A stale worker can finish a remote GET but cannot commit its results.
- One active content/rebuild job per source is enforced through `knowledge_sources.active_job_id` CAS; periodic/manual requests coalesce and return the active job ID. Access checks use their own jobs and may run while content import waits, but must serialize generation/denial commits with activation. Per-library final activation is a short CAS, not a lock held during downloads.
- Inline mode starts the new durable-job poller/due-source scanner in API lifespan; worker mode starts them only in `worker.py`. API endpoints only insert/coalesce jobs in worker mode. Remove knowledge-handler execution from the generic API boot redispatch in worker mode; no accidental dual dispatch. Multiple eligible processes remain safe under DB CAS on both SQLite and Postgres; do not rely on SQLite `FOR UPDATE`.
- Due scanner every 15 seconds atomically advances due time and creates/coalesces a job. On restart reclaim expired leases; retain checkpointed staging and re-read generations. Maximum six worker attempts per content job, excluding deliberate quota waiting before claim; source status becomes blocked afterward, with manual Retry and next scheduled recovery no sooner than 30 minutes. A newer config makes an old job `cancelled`/superseded, not failed.
- Cancellation POST writes `cancel_requested_at`. Check between each page/file/model batch and before activation. A queued job cancels immediately; running work stops at the next boundary or operation deadline. Lease heartbeat continues while unwinding. If activation wins the transaction first, cancellation returns terminal `completed` with `already_activated=true`; otherwise no activation. Denial observations already committed remain effective.
- On graceful shutdown stop claims, signal cancellation of local tasks, checkpoint/fence writes and release/requeue within 30 seconds; after hard crash the lease expires. Database locks never span Google calls. Parser work runs in a bounded subprocess so a timeout actually terminates CPU/memory work; `asyncio.to_thread` alone cannot kill a stuck parser.

### Timeout and quota policy

Settings-only defaults: connect timeout 5 seconds; metadata/OAuth total timeout 20 seconds; file export/download 60 seconds including streaming; parse wall time 30 seconds and 512 MiB subprocess memory; embedding batch 60 seconds; content job wall time 30 minutes per attempt. Exceeding a job deadline checkpoints and retries until its attempt ceiling; per-file timeouts retain typed errors. Cancellation service target is 65 seconds for in-flight operations, except a backend outage delays reporting, never permits unfenced activation.

At most four connector jobs per process, two active sources per owner, two file transfers per connection and eight transfers per process. Persist shared per-OAuth-client and per-Google-sub rate-bucket reservations in `knowledge_rate_buckets(scope_key,window_start,reserved_units,reserved_requests,reserved_bytes)` with PK `(scope_key,window_start)`; CAS reservations enforce budgets across worker processes. Use 60-second windows and a daily-byte window, discard expired rows after 48 hours. Reserve endpoint cost before call, streamed byte budget before each bounded chunk; do not refund uncertain remote requests. Defaults: project 10,000 units/minute and 300 requests/minute; account 2,000 units/minute and 60 requests/minute; project 1 GiB downloaded/day. These conservative operator-tunable budgets are not provider guarantees. Reserve 25% of each minute budget for permission checks/token lifecycle so bulk content import cannot indefinitely starve authorization. API browser browsing shares the same account/project budgets.

**Capacity admission is required before initial activation and before admitting selection/corpus growth.** For each project/account budget bucket, calculate the deduplicated request/unit cost of one complete five-minute authorization pass over all still-allowed retained files, selected roots, ancestors and shared-drive membership pages. Exclude permanently denied epochs, which can never be served. Admit only when the total fits within 80% of that bucket's reserved five-minute request capacity **and** reserved unit capacity; the remaining 20% covers token refresh and retries. Use actual enumerated metadata/page counts, not file-byte size or an optimistic batch-request discount. Reserve at least one connector worker slot for permission/token work; content concurrency cannot occupy it.

With the default 60 account requests/minute and 25% reserved capacity, this permits at most 60 metadata requests per five-minute pass before root/membership overhead, not 2,000 files. The UI reports actual available/required capacity and `access_capacity_exceeded`; operators can raise the local budgets only within their verified provider allocation. Recheck admission when limits or the union of retained authorized files change. A growing folder that exceeds capacity blocks the new activation while existing admitted content continues receipt checks; lowered quota/provider outage still causes reads to fail closed at receipt expiry. Do not call an over-capacity initial sync successful and rely on eventual expiry as normal operation.

Google's [current quotas](https://developers.google.com/workspace/drive/api/guides/limits) distinguish projects under the May 2026 model from grandfathered quotas, and assign 5 units to metadata reads/start tokens, 100 to list calls, and 200 to downloads/exports. Operators must configure the deployment for its actual Cloud Console allocation; do not hard-code the older “12,000 requests/minute” folklore or claim Drive is unconditionally free. Response-reported 403 rate-limit reasons and 429 are transient; permission/admin 403 reasons are not. Handle 5xx/transport errors with up to six request attempts, delay `max(Retry-After, min(2^attempt + uniform(0,1),64))` seconds, cap Retry-After scheduling at one hour before surfacing blocked status, and persist long delays rather than sleeping with a worker slot. A single `Retry-After` above one hour blocks this attempt with the exact retry time; do not call early. Daily budget exhaustion displays `budget_exhausted` and schedules at the next window or operator adjustment. No error text includes provider response bodies containing secrets/document text.

## 9. API contracts

All normal routes require current owner authentication; mutating and account-browse routes additionally require editor role explicitly, including GET browser endpoints. Foreign-owned IDs return 404. Viewer may read existing library/source/job metadata under current ownership but cannot query arbitrary Google files. Callback is the tightly scoped exception in §5. Browser calls use `src/lib/api.ts`; OAuth start/callback flow-cookie handling goes through same-origin Next handlers forwarding headers privately, never auth query parameters.

Errors use `{"detail":{"code":"...","message":"safe human message","retryable":false,"job_id":null,"retry_at":null}}`; ordinary auth middleware may retain its existing 401/403 shape. API client normalization handles both. | `POST /api/knowledge/{base_id}/sources/{source_id}/sync` | `{mode:"incremental"\|"full",expected_config_generation}`, idempotency key → `202 {job_id,coalesced}`. Full is the operator recovery action, not a cursor reset without reconciliation. |
| `GET /api/knowledge/{base_id}/sources/{source_id}/jobs` | Owner-filtered cursor pagination, default 25/max100, immutable chronological summaries and counts. |
| `GET /api/jobs/{job_id}` | Extend shared job response with typed knowledge `phase,counts,error_code,retry_at,cancel_requested_at,revision_id`; never payload secrets/cursors. |
| `POST /api/jobs/{job_id}/cancel` | Owner editor → `202 {job_id,status,cancel_requested_at}` or terminal `200 {status,already_activated}`. |
| `DELETE /api/knowledge/{base_id}/sources/{source_id}` | Expected config generation via `If-Match`; immediate deny + purge job → `202 {status:"disconnected",purge_job_id,affected_release_count}`. Repeated delete is idempotent metadata result. |
| `DELETE /api/knowledge/connections/{id}` | `If-Match` credential generation; same denial for every linked source + revoke/purge → `202 {status:"disconnecting",affected_source_count,remote_revocation_status}`. |
| `GET /api/knowledge/{base_id}/revisions` | Cursor-paginated `{items:[{id,sequence,content_hash,created_at,document_count,chunk_count,active,access_status,referenced_release_count}],next_cursor}`. Denied/purged rows return metadata, not snippets. |
| `GET /api/knowledge/{base_id}/revisions/{revision_id}/documents` | Owner/revision access check, paginated versioned document metadata; full-source details never expose inaccessible content. |
| `POST /api/knowledge/{base_id}/query` | Existing request plus optional `revision_id`; returns §6.3 fields. Omitted revision resolves active once; settings override is labeled preview, not manifest evidence. `knowledge_revision_revoked` → 409; access receipt expired → 503 with access-check job. |

Extend existing library documents responses with stable logical document ID, origin, source/version/revision and status. Existing `/documents/{id}` DELETE remains for manual documents; source-owned IDs return `409 source_managed_document` with the exclusion action. Manual paste/file/URL mutations and reindex on libraries must build/activate revisions through the same service (reindex becomes 202 durable rebuild). Similarly, workflow-local knowledge endpoints (`POST /{workflow_id}/knowledge`, `POST /{workflow_id}/knowledge/upload`, `POST /{workflow_id}/knowledge/bulk`, `DELETE /{workflow_id}/knowledge/{document_id}`, and `POST /{workflow_id}/knowledge/reindex`) must build and activate workflow-scoped KnowledgeRevisions and advance `Workflow.active_knowledge_revision_id` and `knowledge_activation_generation` using the identical transaction and refcount rules. Update existing UI/client callers together; no success response claiming synchronous reindex if it has only queued. User query input, top-K/tag/settings validation reuse current bounds. Source request keys are retained 24 hours; source creation's unique library/connection identity prevents accidental duplicate sources even after key retention expires.

## 10. Security, privacy, retention and observability

- Connector processes only files selected by this owner under this grant. Jobs reconstruct owner context from stored source ownership; never accept `user_id` from untrusted job payloads. No cross-user content/embedding dedupe or cache sharing. API-key rotation mapped to the same user preserves ownership; changing the map must not transfer someone else's Google grant implicitly.
- Connected knowledge is untrusted data, never instructions to tools or the connector. Do not execute macros, fetch Markdown links, follow arbitrary download URLs, or send Drive bearer tokens to `webViewLink`. Connector HTTP is restricted to fixed Google API/OAuth hosts. HTTP redirects from authenticated downloads are refused unless an explicitly vetted Google transport path is implemented without forwarding credentials to other origins; no generic URL-fetch fallback.
- Google API User Data Policy and restricted-scope Limited Use obligations apply to stored text and model transmission. Consent explains embedding/rewrite/rerank and workflow-model processing, not just “sync.” Default local retrieval avoids embedding transmission; connecting does not grant permission to train models or export data to analytics. Workflow execution remains subject to its existing configured model/service permissions. No production credential or Drive token is sent to the diagnosing model in run repair.
- Raw download/export bytes live only in bounded memory or owner-restricted temporary files; delete at the end of each file attempt, and sweep abandoned temporary files on worker startup. Persist parsed chunks/version metadata, not original binary uploads or whole provider permission objects. Do not log text, token payloads, OAuth codes, cursor values or filenames by default.
- Denied content is blocked synchronously and physically purged from chunk text, JSON vectors, mirror indexes, staging data and caches within **24 hours** regardless of revision refs. Keep minimal revision hashes/IDs/tombstone reasons to explain blocked releases; refs protect normal reproducibility retention, never revoked bytes. Purge retries are durable and alert if overdue. Reconnecting cannot read purged content or remove old tombstones.
- Normal unreferenced revisions retain for **30 days**; active or referenced allowed revisions retain until reference removal. Document versions/chunks are refcounted through membership; GC uses a DB transaction to prove no live members/refs before deleting. Purge all failed/cancelled unreferenced staging within 24 hours, sync logs/non-secret item errors after 30 days, OAuth attempts within one hour, revocation tokens within 24 hours. Deleting a library denies first and retains only tombstone/reference metadata needed by extant manifests.
- Provenance-bearing run/checkpoint/session/fixture content is authorization-filtered before it is returned or replayed. If downstream derived output cannot be safely separated from denied knowledge, redact the entire derived payload and retain status/counts/hash-only evidence. Add dependency IDs at context propagation boundaries, rather than trying to discover copied passages with substring scanning. The same rule governs exported trace/report downloads generated after denial. Already delivered browser responses, external model requests, user exports and third-party logs cannot be recalled; disclose that limit and do not claim remote erasure. Production backups must be encrypted and age out within **30 days**; restore must apply retained tombstones before serving traffic. External export retention is the operator's responsibility and must be disclosed before enabling connector processing.
- Audit events: connection initiated/completed/reauth-required/disconnected, source selected/selection-changed/excluded, sync started/retried/cancelled/failed, revision activated, access denied, purge completed/overdue. Payloads contain owner/resource IDs, counts, timings and safe reason codes only. Do not include names/paths/tokens/text.
- Metrics: queue age, content lag, access-receipt-expiry count, sync/file latency, changed/skipped/failed files, revision activations/no-ops, lease recovery/fence rejection, quota units/bytes, retry count by safe provider code, revoked reads blocked, purge backlog age. Dimensions are bounded provider/operation/status, not remote file IDs. Source UI supplies per-source details; application observability need not mirror an entire Drive audit log.

Create logical documents, sealed `legacy_import` versions and one initial revision per library and per workflow with knowledge, using existing settings, then atomically set `KnowledgeBase.active_revision_id` or `Workflow.active_knowledge_revision_id`. The legacy embedding family is `legacy_unknown`, not guessed from dimension. Existing previews can retain legacy behavior with an explicit label; a quality-gated manifest using vector retrieval requires reindex into a declared profile first, while a lexical-only manifest can pin existing text. 5. **API/UI and operational setup.** Add route schemas, typed client methods, OAuth same-origin routes, Source section/activity drawer, keyboard-accessible browse/selection and disclosure/confirmation states. 6. **Public enablement.** Enable only when initial sync, incremental updates, receipt enforcement, crash/cancellation recovery, disconnect purge and release pinning acceptance scenarios all work. ## 12. Observable acceptance criteria

The implementation must add deterministic provider-adapter fixtures for the cases below and a real Google test-account end-to-end smoke flow, without calling real workflow write tools during release/repair evaluation. Tests are proposed here; none were executed for this specification.

| Scenario | Observable result |
| --- | --- |
| Connect succeeds/declines/partially grants; wrong state/cookie/nonce/audience; replay callback; initiating editor key revoked before completion | Only matching, current authenticated owner completion creates a connection. Decline/partial scope fails visibly, callback replay cannot install tokens twice, no secrets in logs/redirect/API response. Viewer and anonymous requests cannot connect/browse. |
| Encryption missing/invalid; decrypt key lost; same-account refresh concurrency; reconnect with a different Google account | Connector setup/reads fail closed without plaintext. Exactly one installed refresh result wins fencing, omitted refresh token preserves the old one, normal token rotation does not stale quality checks. Account switching cannot overwrite a grant. |
| My Drive and shared-drive recursive roots overlap; duplicate names; a shortcut cycle; shared-drive item for a non-member | One document per source/file ID, all direct descendants discovered through paging, no shortcut traversal, non-member selection rejected with stated restriction. No content outside roots downloaded. |
| Empty intermediate list page has a next token; token rejected; `incompleteSearch=true`; discovery limit crossed | Continue paging; restart/dedupe rejected folder pagination; incomplete/capped scans never infer mass deletion or activate partial content. UI exposes precise error/counts. |
| Each allowed MIME; unsupported Sheet/Slide/image; 9 MiB file; export limit error; oversized extracted text; scanned/encrypted PDF; DOCX expansion | Exact export/parser policy applied. Unsupported files counted before download. Size/truncation/parse cases visible and block accepted-file activation until excluded/fixed; no silent first-sheet or OCR claim. |
| Drive file changes during initial listing or download | Pre-enumeration token replay picks up changes; pre/post provider-version check discards inconsistent bytes. Repeated change surfaces `file_changed_during_download`, not false success. |
| Initial indexing fails halfway; reader polls repeatedly | No staged chunk is returned. Existing active revision stays unchanged; new library remains empty. Explicit file exclusion permits a complete rebuild, not an implicit partial pass. |
| Rename/content edit/no-op repeated pages; two overlapping roots | Rename preserves logical identity; content creates one version/new revision; identical content/config creates no duplicate revision; cursor replay does not duplicate chunks. |
| File/folder moves into/out of selection; parent capability change without child changes; shared-drive-only edit/member removal | Descendant membership/capabilities are recomputed, user+drive logs consumed, and lost access denies old pinned revisions. A retryable API error is not interpreted as deletion. |
| Google returns `removed` but file still exists in another corpus | Current metadata/membership determines retain versus deny/quarantine; no assumption that `removed` means globally deleted. Corpus-changing selected root requires explicit reselection. |
| Concurrent manual ingest and two source completions | CAS/rebase retains every unrelated contribution, seals one consistent membership per activation, enforces final 5,000-chunk cap, and commits only matching cursor/source generation. |
| Worker killed after chunk write, after staged page, and immediately before/after activation; expired worker resumes | Recovery replays idempotently; stale lease cannot write. Content/cursors never split-commit; successful activation is visible exactly once as a local state transition, without claiming remote exactly-once calls. |
| Cancel queued/running/finalizing job; edit roots while old worker runs; pause updates | Queued cancel immediate; active operation bounds honored; cancelled/superseded worker never activates. A winning activation is reported as already activated. Pause still validates permissions. |
| Repeated 429/403-rate-limit/5xx; permission 403; long Retry-After; daily local budget exhausted | Correct retry classification/backoff, durable retry times, no sleeping worker monopolization, no credential-error retry loop, no budget overrun across two processes. Authorization validation retains reserved capacity. |
| Selected/growing corpus or lowered budget exceeds receipt-validation capacity | Admission computes project/account request and unit demand including retained allowed members and ancestor checks; over-capacity content never activates. Existing content keeps prioritized receipt checks and fails closed on expiry; the UI names required versus available capacity rather than falsely promising the hard file cap. |
| Provider outage or worker stopped for >15 minutes after successful sync | Old content age remains visible but every affected revision read returns access-unverified after per-member receipt expiry; no unlimited stale-authorized fallback. |
| Local source delete/disconnect/exclude and remote loss detected during a failed job | Immediate denial independent of activation/cancel; pinned release and cached query blocked; cursor remains safely replayable; removed chunks purge within 24 hours despite refs. |
| Content advances R1→R2 after an R1 quality-gated publication | Released runs retrieve R1, preview uses R2, UI reports mismatch; a new protected publish checks current dependencies. Reconnect/untrash never silently restores an old denied R1. |
| Revocation while retrieval result is cached or model/evaluation work is in flight | Access-generation completion check suppresses newly returned derived content/evidence; cached/replayed fixture/session/checkpoint cannot bypass. Already externally delivered data is explicitly not claimed recalled. |
| Foreign-owner library/source/job/revision ID, copied query cursor, or source created with another owner's connection | 404/no content/no provider call; cursor binding enforced. No filenames, counts or credentials leak across owners. |
| Active/refcounted revision GC, revoked content GC, library deletion, backup restore | Allowed referenced content retained; revoked bytes deleted regardless of refs; metadata explains blocked release; restoration applies tombstones before reads. |
| Fresh SQLite and Postgres migration plus upgrade from populated manual libraries | Original text/citations/settings preserved, active revision created without Google calls, no numeric UUID coercion, no duplicate lease migration, gated vector manifests reject unknown legacy embedding profile until explicit rebuild. |
